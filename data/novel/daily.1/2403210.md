对于给定的 HTML 模板，只需按照同一套 Schema 提供结构化数据就能够同时渲染多个对应的页面。在多数情况下，如果只是数字、词汇和单行描述等信息，直接编写作为最终输出的 JSON 文件尚能招架；而当模板中出现了段落乃至文章等结构时，基于简单类型的数据提供对于页面的丰富性构建就开始显得乏力了。

## 下位替代

- *__手动编写 HTML__*

  似乎能行，但难以维护。

- *__在字符串中嵌入换行符，将分割段落的任务交给模板__*

  能行，但只能行一点点。

- *__提供原始 Markdown 文本，遍历每个属性并扔给解析器过一遍__*

  虽然 YAML 之类的可以在字符串里显式换行，但依然不够优雅，而且判断属性是否需要被转换也会产生额外的成本。

## 解决方案

以上方案都将文本内嵌在其他数据格式的对象中，难以获得编写 Markdown 的原生开发体验。既然如此，如果能在开发时像写普通的 Markdown 文档一样自然，而在构建时将经过处理的 HTML 字符串自动填充到对应的属性中，就能够一并解决所有的问题了。

毫无疑问，此时的最优解为自定义 Markdown 解析器。

首先需要明确的是，我们并不需要输出纯粹的 HTML 文档，而是将需要转换成 HTML 的字段选择性地交给 Markdown 解析器，这意味着这项工作的重点不在于对解析器本身进行复杂的重构（并且在这方面，MDC / MDX 已经做得很充分）。

那么对于不需要转换的属性，则首先可以自然而然地放置在 Frontmatter 中了：

```md
---
title: 浅井爱纱
---
```

在解析 Markdown 前，先从文档中提取 Frontmatter 作为基对象：

```ts
const { attributes, body } = fm<FrontMatter>(md);
```

那么接下来，该如何指定有哪些属性需要被解析呢？答案是 dot-notation，即点表示法：

```js
"obj.foo[0].bar";
```

只需要想办法将这种风格的字符串与其对应的属性值组合在一起，后面的事就可以交给 Markdown 解析器了。

此时，具体的实现有这样两种思路：

*__1\.__* 将 dot-notation 字符串作为 HTML Attribute 值放置在约定好标签名的元素中，使用 MDC 等扩展语法处理原始文本；解析生成的 HTML 文档，获取所约定的元素，建立 dot-notation 所指向的属性与 ``innerHTML`` 的映射。

*__2\.__* 创建自定义语法，将上述映射直接作为解析结果返回。

下面仅对后者进行讲解，这也是本网站实际采用的方案。

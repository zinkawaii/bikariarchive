*模板化*和*组件化*是 Web 开发中两种常见的开发模式，尽管它们并不对立甚至高度相关，但无论是在抽象层面还是实现细节上，都根据架构思维的不同存在着决定性的差异。

## 模板化 - Template -

模板化是一种将页面结构抽象为可复用的模板的技术，它允许开发者定义页面的结构，并在运行时根据所传入的数据动态生成实际的页面。

### 核心

模板化通常依赖于模板引擎，如 EJS、Handlebars、Nunjucks 等。这些引擎大多提供了特定的语法结构，使得开发者能够轻松地利用其语法糖快速组装页面逻辑，并在解析文件时应用传入的数据，最终生成 HTML 页面。

### 特点

1. 学习成本低

   只需掌握任意一门模板语言，即可轻松加入模板化的开发，而其余的部分能够通过原生的 JS + CSS 技术实现。

2. 关注点分离

   页面结构和业务逻辑可以单独处理，两者之间通过数据桥接，修改 HTML 结构无需改动 JS 逻辑。

3. 服务端渲染

   模板的解析通常发生在服务端，客户端接收到的是完整的 HTML 页面。

### 应用场景

1. SSR

   模板化是一种较为传统的技术手段，它非常适用于在服务端处理用户请求时，根据传参的不同来动态渲染页面，最后将静态的 HTML 页面返回到客户端。

2. SSG

   静态网站生成类似于预先准备好请求的数据，然后让服务端一次性渲染所有的页面，同样和模板化的开发模式相契合。

## 组件化 - Component -

组件化关注于构建独立可重用的 UI 组件，是目前流行的众多前端框架中最主要的概念。

### 核心

组件化依赖于特定的 UI 框架，如 Angular、React、Vue 等。它能够将 HTML 结构、CSS 样式和 JS 逻辑封装成一个独立的实体，而能够在页面的各个不同的地方重复使用。

### 特点

1. 封装与重用

   组件将 HTML、CSS 和 JS 封装在一起，使得它能够作为一个独立的模块组装在页面的任意位置。

2. 强交互

   组件通常具有复杂的交互逻辑，而不仅仅是对静态数据的展示。

3. 客户端渲染

   组件通常由浏览器的 JS 动态生成和管理 DOM 元素。

### 应用场景

1. SPA / CSR

   组件化适用于单页面应用的开发与构建，它使得网页具有丰富的交互逻辑与状态管理。

## 模板化 VS 组件化

1. 宿主环境

   - 模板化常在服务端执行，将静态 HTML 返回客户端。

   - 组件化常在客户端执行，动态生成 DOM 树。

2. 设计与功能

   - 模板化侧重于页面布局，以静态内容与数据的展示为主。

   - 组件化侧重于 UI 重用与交互，可能包含复杂的业务逻辑。

3. 学习曲线与技术栈

   - 模板化的学习门槛低，除模板引擎的简单语法外，以传统的 HTML + CSS + JS 为主。

   - 组件化需要学习现代前端框架，对开发者的代码素质要求较高。

## 模板还是组件？

**_正文开始。_**

事实上，将组件化的思想单独剥离为一种开发模式是不合理的，因为绝大部分框架都不仅限于对组件的封装，而是提供了从组件（Component），到布局（Layout），再到页面（Page），这样一套完整的结构路线。模板化页面布局的思路，在组件系统中同样受效。

不仅如此，组件通常包含了以特定的语法构建的模板，如 Vue 的 ``<template>``、React 和 Solid 的 JSX、Angular Template、Svelte Template 等等，它们同样是具有相似功能的模板引擎。只不过在组件系统中，框架额外引入了一套用于处理模板与数据交互以及如何响应式地更新 DOM 树的运行时（例外地，Svelte 在编译时做好了这一切），这是使得组件化远远复杂于模板化的主要原因之一。

组件化也可以做 SSR 和 SSG。既然它们内部利用了模板引擎，那么将模板直接转为 HTML 字符串而不是虚拟 DOM 也是可能的。实际上，大部分框架都暴露了这样的方法，使得服务端能够预先生成首屏 HTML，在返回到浏览器时由 JS 激活 DOM 树完成一次水合（Hydration），从而实现服务端渲染或是静态站点生成。它并没有落后于模板化的道理。

模板化之所以容易上手，和它的轻量与直观脱不开干系。相对于一套完善的框架，学习模板只需要掌握其为数不多的语法格式，便可以轻松打造自己想要的页面——这也导致了它难以取得较高的上限。模板对静态内容的生成天然利好，而一旦想要向其中注入动态的内容，就不得不使用 JS 在外部操作 DOM，这在无形之间又形成了一种耦合。那么是要引入组件吗？对于页面中不变的部分，使用模板预先生成；需要动态操作的部分，则使用组件来控制：思路很好，这也是 Astro 的核心理念。然而，Astro 本身也是一种组件系统，它的模板与组件相结合同样是受限于框架内的。即想要传统的模板化，又想要现代的组件化，这就已经陷入了高耦合的泥沼。Typescript 官方一度推荐使用 ``interface`` 而不是 ``type``，而对于许多特定的需求，又只有 ``type`` 能够胜任；最终在实际开发中，便混杂了 ``interface`` 和 ``type`` 两种语法。我认为这两者是有共通之处的。

模板化的优点，主要还是在于足够轻量。服务端和客户端都不必加载繁重的运行时，开发者也不必被锁定在某一门框架语言中。一旦适应了某一类框架的开发思维，想要迁移到另一类框架中便需要克服更多的困难。而模板化的思路是通用的，它只是单纯地提供一个模板，然后由服务端渲染为 HTML 而已。

## 模板就是组件

模板当然是组件。既然一个模板能够引用其他的模板，那么对于它而言，后者就是一个被重用的组件；而当一个模板被引用时，它与外界的接口也仅仅是所需要的数据，因为内部的页面逻辑都被封装好了；既然能够生成 HTML，那么样式也同样能够直接包装在 ``<style>`` 标签中。这样一来，模板不就仅仅是缺少了交互的组件吗？模板系统，说到底就是一个组件系统。假如我们对 EJS 稍作修改，使得内部的 ``<script>`` 标签能够获取模板内部的上下文；在渲染整个页面时，去除相同模板内重复的 ``<style>`` 标签：一个简陋的组件化前端框架就此完成了！

反过来讲，组件系统是模板系统的进化，学习模板化的开发思路，也是在变相学习组件化的开发思路。既然前端框架难以入门，那么从模板应用开始学习是极好的选择。它既能够培养现代化的开发思想，又能够提供更加原生的前端环境，使得初学者深入理解页面生成的运行原理，产生更加浓厚的兴趣，而不受被高度封装的各类框架纷扰，对着复杂的构建流程望而却步。
